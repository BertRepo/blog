## 为什么需要 RAG

大语言模型(LLM)虽具备强大的语言理解与生成能力,但在企业落地时面临三个结构性难题:

- **知识截止(Knowledge Cutoff)**:模型参数在训练完成后即冻结,无法感知此后的事件。一个 2024 年训练的模型,对 2026 年的产品规格、API 变更一无所知。
- **幻觉(Hallucination)**:模型以"概率续写"方式生成,缺乏事实校验机制,会一本正经地编造看似合理却错误的细节。
- **不可追溯**:纯参数化知识无法定位来源,用户无法核实答案依据,这在医疗、法律、金融等场景不可接受。

面对领域知识更新,业界有两条路径:**微调(Fine-tuning)**与 **RAG(检索增强生成)**。

| 维度 | 微调 | RAG |
|---|---|---|
| 知识时效 | 需重新训练 | 实时更新(改库即可) |
| 成本 | 算力+数据标注高 | 向量化+检索,成本低 |
| 可控性 | 难以删除/修正 | 删改文档即可 |
| 长尾/私有知识 | 内化进权重 | 外置知识库 |
| 幻觉控制 | 仍会幻觉 | 有引用可溯源 |

一句话:微调改变模型"能力与风格",RAG 改变模型"知道什么"。二者并非互斥,常组合使用。

## RAG 基本架构

RAG 的核心思想是**把"检索"作为生成的前置步骤**,用外部知识库为模型提供上下文。数据流可拆为四个阶段:

```
[离线索引 Indexing]
  文档 → 切分 Chunking → 向量化 Embedding → 存入向量库(含 ANN 索引)

[在线检索 Retrieval]
  用户 Query → 向量化 → ANN 检索 top-k → (混合检索/重排序) → 候选片段

[增强 Augmentation]
  候选片段 + Query → 拼装 Prompt(含指令、引用、上下文)

[生成 Generation]
  LLM → 答案(带引用)
```

索引阶段离线一次性构建并持续增量更新;检索-增强-生成阶段在线实时执行。这条流水线看似简单,每个环节都藏着一堆工程玄机。

## 向量嵌入 Embedding

语义检索的根基是:**语义相近的文本,在高维空间中向量也相近**。

嵌入模型(Embedding Model)将变长文本映射为固定维度的稠密向量,如 `bge-large-zh`(1024 维)、`text-embedding-3-large`(3072 维)。这个向量不是随机的,而是被训练成"语义距离"的代理。

**训练原理:对比学习**。以 SimCSE 为例,同一句话两次过 Dropout 得到两个"正样本"对(语义应相近),同 batch 内其他句子为"负样本"(语义应相远)。损失函数拉近正对、推远负对:

```
# 对比学习简化伪代码(SimCSE 思路)
z_i  = encoder(x_i, dropout)   # 正样本1
z_i' = encoder(x_i, dropout)   # 正样本2(同句,不同dropout)
# batch 内其余 z_j 为负样本
loss = -log( exp(sim(z_i,z_i')/τ) / Σ_j exp(sim(z_i,z_j)/τ) )
```

经过大规模语料训练后,向量空间呈现出有意义的几何结构:"猫"与"狗"的向量夹角小,与"汽车"夹角大。这就是语义检索能用余弦相似度排序的原因。

**相似度度量对比**:

| 度量 | 公式 | 特点 |
|---|---|---|
| 余弦相似度 | `cos(A,B)=A·B/(|A||B|)` | 只看方向,对模长不敏感,最常用 |
| 点积 | `A·B` | 归一化后等价余弦;未归一化时模长大者占优 |
| L2 距离 | `‖A-B‖₂` | 衡量绝对距离,对模长敏感 |

实践中嵌入向量通常做 L2 归一化,此时三者数值上等价(点积=余弦,L2²=2-2·余弦)。选哪个主要看索引库的实现约定。

## 向量数据库与 ANN 索引

暴力 kNN(k-Nearest Neighbor)要遍历全库 N 个向量逐一计算相似度,复杂度 O(N·d)。当 N=千万级、d=1024 时,单次检索动辄数百毫秒到秒级,在线服务不可接受。

**ANN(Approximate Nearest Neighbor,近似最近邻)**用空间换时间:允许极小的精度损失(召回率 95%+),换取几个数量级的延迟下降。

### HNSW:分层小世界图

HNSW(Hierarchical Navigable Small World)是目前最主流的 ANN 算法,Faiss/Milvus/pgvector/Qdrant 均支持。它借鉴了**跳表(Skip List)**的分层思想:

- 图分多层,上层稀疏(长距离边,用于快速跨区域跳转),下层稠密(短距离边,用于精细定位)。
- 每个节点都出现在最底层;上层节点是下层节点的子集,逐层抽样。
- 搜索从最顶层开始,沿边贪心逼近 query,逐层下沉,在最底层做精细 kNN。

```
# HNSW 搜索简化伪代码
function search(query, k, efSearch):
    entry = 顶层入口节点
    for layer from topLayer down to 1:
        entry = greedy_search(layer, entry, query)   # 贪心找最近
    # 最底层用动态候选集 efSearch 扩大搜索宽度
    candidates = beam_search(layer=0, entry, query, ef=efSearch)
    return top_k(candidates, k)
```

关键参数:

- `M`:每层每个节点的最大邻居数(图密度)。M 越大召回越高、内存越大,常用 16~48。
- `efConstruction`:建图时搜索宽度,影响索引质量与构建耗时。
- `efSearch`:查询时搜索宽度,≥ k。调大提升召回、增加延迟,是查询期可动态调整的旋钮。

### IVF:倒排+聚类

IVF(Inverted File)先用 k-means 把向量空间聚成 `nlist` 个簇,每个簇维护一个倒排列表。查询时只扫描离 query 最近的 `nprobe` 个簇(`nprobe << nlist`)。

- `nlist`:簇数,通常取 `√N` 量级。
- `nprobe`:探测簇数,调大则召回↑、延迟↑。

IVF 常与 PQ 组合(IVF-PQ):先用 IVF 粗筛簇,再在簇内用 PQ 压缩向量做细排,极致省内存。

### PQ:乘积量化

PQ(Product Quantization)把 d 维向量切成 m 段,每段独立用 k-means 量化成一个码字(通常 256 类,1 字节)。一个 1024 维 float32 向量(4096 字节)经 PQ(m=64)压缩到 64 字节,约 64 倍压缩,代价是相似度变成近似计算。

| 索引 | 召回 | 延迟 | 内存 | 构建速度 | 适用场景 |
|---|---|---|---|---|---|
| HNSW | 极高 | 极低 | 高(存原图) | 中 | 中小规模、低延迟首选 |
| IVF-Flat | 中高 | 低 | 中 | 快 | 大规模、可接受调参 |
| IVF-PQ | 中 | 低 | 极低 | 快 | 超大规模、内存敏感 |

## Chunk 切分

检索的基本单位是 chunk,不是整篇文档。切分质量直接决定检索上限——检索器找不到完整答案,再强的 LLM 也无米下锅。

常见切分策略:

- **固定大小切分**:按字符/token 数滑动窗口。简单,但可能切断句子、段落。
- **递归字符切分**(LangChain `RecursiveCharacterTextSplitter`):按 `["\n\n", "\n", " ", ""]` 优先级递归切,尽量在自然边界断开。
- **语义切分**:用嵌入模型计算相邻句子相似度,在相似度骤降处断开,保证块内语义连贯。
- **按结构切分**:Markdown/HTML 按标题层级切,代码按函数/类切,保留结构元数据。

`chunk_size` 与 `overlap` 的权衡是核心:

| | 太小 | 太大 |
|---|---|---|
| 检索 | 命中精准但语义碎片化 | 噪声多,相关度稀释 |
| 生成 | 上下文不完整 | 易超 LLM 窗口、被截断 |
| 数量 | chunk 数膨胀,索引大 | chunk 数少,索引小 |

经验值:chunk_size 256~512 token,overlap 10%~20%。结构化文档优先按结构切,再辅以大小约束。

## 检索策略增强

朴素 top-k 向量检索有明显短板:对短 query、关键词命中型问题(如"报错码 E-4012")反而不如传统全文检索;且只召回字面/语义相近片段,缺少全局视角。

**混合检索(Hybrid Search)** 结合稀疏检索(BM25)与稠密向量检索,用 RRF(Reciprocal Rank Fusion)融合:

```
# RRF 融合,k 通常取 60
score(d) = Σ_path  1 / (k + rank_path(d))
```

RRF 无需归一化不同检索器的分数,实现简单,是工业界最常用的融合策略。

**查询改写/扩展**:

- **HyDE(Hypothetical Document Embeddings)**:先让 LLM 为 query 生成一个"假想答案文档",再用该文档的向量去检索——因为"答案"与"答案"的语义距离通常比"问题"与"答案"更近。
- **子查询分解**:把复杂问题拆成多个子问题分别检索,再合并结果。

**元数据过滤**:先按 source、时间、部门等元数据过滤,再做向量检索。既能缩范围,又能实现权限控制。很多向量库支持 pre-filter(先过滤再 ANN)与 post-filter(先 ANN 再过滤),pre-filter 更稳。

## 重排序 Rerank

向量检索用的是 **bi-encoder(双塔)**:query 和 doc 各自独立编码,相似度用点积算,速度快但 query-doc 交互弱。

Rerank 用 **cross-encoder(交叉编码)**:把 `[CLS] query [SEP] doc [SEP]` 拼成一个序列喂给模型,全注意力交互,精度高但计算量 O(N)(每对都要过一次模型),无法用于全库。

工业标准两段式:

```
全库(百万级) ──bi-encoder ANN 粗排──> top-50~100 ──cross-encoder 精排──> top-5~10
```

cross-encoder 能把 bi-encoder 召回的弱相关项重新打分,显著提升精度。常用模型:`bge-reranker-large`、`Cohere Rerank`。代价是额外 50~200ms 延迟,需在质量与延迟间权衡。

## 上下文组装与生成

检索到的 chunk 怎么拼进 prompt,直接决定生成质量。

- **引用溯源**:每个 chunk 带编号(如 `[1]`),要求 LLM 在答案中标注引用,便于核验。
- **上下文丢失(middle lost)**:LLM 对 prompt 开头和结尾更敏感,中间内容易被忽略。对策:把最重要的 chunk 放首尾,或按相关度升序排列(最相关放最后,紧邻 query)。
- **指令设计**:明确"仅依据上下文回答,不知道就说不知道",抑制幻觉。
- **超窗口处理**:超过上下文窗口时,优先裁剪低相关度 chunk,或用 map-reduce 式摘要。

```
你是一个严谨的问答助手。仅依据下方【上下文】回答【问题】,
若上下文不足以回答,请回答"根据已知信息无法回答"。
每个事实陈述后用 [编号] 标注引用来源。

【上下文】
[1] ...
[2] ...

【问题】
{query}
```

## 评估

RAG 需要三元评估:

| 层级 | 指标 | 含义 |
|---|---|---|
| 检索质量 | Recall@k、MRR、NDCG | 相关 chunk 是否被召回、排序是否靠前 |
| 生成质量 | Faithfulness、Relevance | 答案是否忠于上下文、是否切题 |
| 端到端 | 答案正确性、引用准确率 | 整体效果 |

- **Faithfulness(忠实度)**:答案中每个 claim 能否被检索上下文支持,衡量幻觉。
- **Relevance(相关性)**:答案与问题的相关程度。

工具上,**Ragas** / **TruLens** 提供自动化评估框架,用 LLM-as-judge 批量打分。建议建一个标注好的 golden set 持续回归。

## 工程实践与避坑

- **增量更新与删除**:文档更新后,旧向量不能残留(检索到过期内容比没有更糟)。用稳定 ID(如内容 hash)做 upsert,删除时同步清理索引节点。HNSW 删除较重,常用"标记删除+周期重建"。
- **向量版本管理**:嵌入模型升级后维度/语义空间变了,旧向量与新 query 不可比,**必须全量重索引**。设计时把 `embedding_model` + `version` 写进每条记录,支持灰度切换。
- **多租户**:用 collection 或 partition 隔离不同租户,配合元数据过滤实现权限,避免单一大索引导致跨租户泄露。
- **缓存**:query 嵌入、检索结果、生成答案三级缓存。高频 query 命中缓存可省大量算力。
- **成本**:嵌入调用、向量库存储、LLM 生成是三大成本项。PQ 压缩省存储,prompt 裁剪省 token,小模型做粗筛省推理费。

## 小结

RAG 把 LLM 从"封闭参数库"变成"连接外部知识的推理引擎"。它的力量不在某个单点算法,而在**整条链路的系统工程**:嵌入质量、索引结构、切分粒度、检索融合、重排序、上下文组装、评估闭环,任何一环拉胯都会拖垮全局。

理解原理比套框架更重要:知道 HNSW 的 `efSearch` 调什么、chunk_size 为什么是 512、为什么需要 rerank、RRF 怎么融合,才能在真实业务里做对取舍。RAG 没有"最佳实践"模板,只有在评估指标指引下的持续迭代。
